# Engineering conventions

The rules the published application is built to, and the checks that enforce
them. Tracked and published because the accompanying manuscript asserts several
of them, and a claim in a paper should be checkable in the artefact the paper
cites.

Internal conventions that the paper does not assert (product scope, editorial
register, brand colour roles) are kept separately and are not part of this
repository.

## Writing

**Never use an em dash.** Not in UI copy, code comments, commit messages,
documentation, or PR descriptions. Use a full stop, a colon, a semicolon, or
parentheses instead. This is enforced by `npm run check:style`, which runs in CI
and fails the build on any occurrence.

An en dash is permitted only as a range or compound separator, where numerals or
words sit on both sides: `100–1,000`, `log10–log10`. Never as sentence
punctuation.

## Attribution

**No tool attribution anywhere in the repository.** Not in commit messages,
commit trailers, author or committer fields, branch names, pull request titles
or bodies, code comments, or documentation. No assistant name, no vendor name,
no model identifier, no "generated by" or "co-authored by" line naming a tool.

The work is the project's, and the commit log is a record of what changed and
why. A tool credit in it is noise to every future reader, it dates the file
against a product name that will move, and on a public repository it becomes
part of the permanent record and of the contributor list.

The rule is about **attribution**, not about the words. A crawler user agent
named in the robots policy, a vendor named in a licence comparison, a model
named in a passage the guidance corpus is actually about: those are subject
matter, and they stay. The test is whether the mention credits or identifies
the tooling that produced the change. If it does, remove it.

Two things this rule cannot reach, and both are worth knowing. Authorship
already written into history is not fixed by a convention, only by a rewrite or
by leaving it. And where an external platform requires a disclosure on posts
made through it, that requirement sits outside this repository and is not
something a project convention overrides; keep it out of anything that lands in
git.

## Privacy

Privacy is the product, not a feature. Four invariants, all enforced by tests
rather than by policy:

1. **No user data leaves the browser.** No telemetry, no error reporting, no
   analytics, no model API.
2. **No third-party origin.** Every byte is served from our own origin.
   Typefaces are self-hosted, never loaded from a font network.
3. **Local storage is disclosed and erasable.** The user can see exactly which
   keys are written and clear them.
4. **The content security policy permits `'self'` only.** The single relaxation
   ever permitted is `'wasm-unsafe-eval'` in `script-src`, for on-device
   inference, which grants no network capability.

`npm run check:privacy` fails the build on an external origin in the CSP, an
external URL in `index.html` or the bundle, or a network primitive in `src/`.
`npm run check:network` then proves it at runtime: it serves the production
build with the real CSP applied, drives a full session in a browser, and fails
on any request to another origin. String analysis is the early gate; the runtime
assertion is the guarantee.

## Determinism

No language model output ever reaches a computed value. All numbers come from
pure functions over user input, and a test asserts that repeated evaluation of
identical inputs produces identical results.

## Fixtures

**A fixture must be drawn from the distribution the code will meet, not
constructed for convenience.** This has now cost us twice.

Settings persisted by an earlier release have keys the current one does not, and
every fixture was written by hand with all keys present, so a whole class of
migration bug was invisible until a returning user found it.

Every design used to test the curvature estimator was symmetric about its mean,
because an evenly spaced ladder is the obvious thing to type. A real bead
standard is unevenly spaced and therefore skewed, and the third moment that an
even ladder sets to zero is exactly the term the estimator was getting wrong.
329 tests passed over a coefficient that was out by up to 99 percent.

A third: no fixture scaled both coordinates of a single standard population,
because a typo is usually imagined as one wrong cell. Scaling both moves the
point along a line of slope one, so every diagnostic in the suite improved
rather than degraded and a calibration built on an intensity of 1.21e8 reported
itself valid.

All three had the same shape: every fixture shared a convenient property that real
input does not have, so the suite agreed with the code about a case neither had
seen. When writing one, name the property that makes your example easy and ask
whether real data has it, and write that property down in a comment beside the
fixture so the next reader can check it rather than infer it. Where a shipped
artefact exists, use its actual numbers: the worked example's own skew is -0.30,
and writing that down is worth more than any ladder.

## Assertions

An assertion nobody has watched fail is not evidence. Before an assertion is
finished, change the code so that the defect it describes is present again, and
confirm it fails for that reason. Mutation notes belong in the commit message.

Two ways this goes wrong, both seen here. A build that fails leaves the previous
bundle in place, so a mutation run silently checks the old artefact: gate the
run on the build succeeding. And an assertion can pass for a reason other than
the one intended, so make the mutation minimal and read the failure text.

## Commands

```sh
npm run verify     # everything below, in order
npm test           # unit tests
npm run check:style
npm run check:privacy   # static: no external origin anywhere
npm run check:network   # runtime: nothing leaves the origin
npm run build      # static site to dist/
npm run build:single
```
